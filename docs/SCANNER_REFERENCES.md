# Local scanner references

Local recognition references are optional descriptors derived from a user photo to help future scans of a user-confirmed card. They are separate from Binder records and never establish or mutate Binder identity.

The reference store accepts a versioned compact-descriptor representation (currently a fixed-width perceptual-hash value) and a source-scoped catalog identity (`catalogProvider` + `catalogId`, with optional `gameKey`). New records cannot store arbitrary binary or Blob payloads as descriptors; existing legacy binary descriptors are readable only as local records and cannot be marked account-owned. Catalog IDs are not assumed to be globally unique. The store does not create descriptors or include a visual recognizer.

A user selects or captures an image, then can choose **Save as recognition reference**, search the catalog, and manually select the exact card and printing shown in the image. The user must explicitly confirm that selection before a compact recognition descriptor, catalog identity, and provenance are saved; the original photo is not persisted. If an active reference already exists for that identity, another reference is not created. If only inactive references exist, the user must explicitly confirm either reactivation or replacement. Reactivation preserves the existing reference and its descriptor. Replacement requires explicit confirmation, creates a new reference from the selected image, and leaves the replaced reference retired. Only active references are returned for matching. Provenance records the user confirmation method and recognition sources when available.

On-device matching reads active references already present in the local IndexedDB store. Both `local` and `account` ownership scopes are eligible when their compact descriptor is available there; account scope does not trigger a fetch or any other network access during recognition. Ownership metadata is preserved for persistence and future sync decisions. Legacy binary descriptors and unsupported descriptor versions are excluded from matching.

References carry an ownership scope: `local` is device-local, while `account` marks user-owned reference metadata/descriptors as a candidate for future account sync. New references default to `local`; older records without this field are read as `local` and are not rewritten. Account scope does not identify or imply a particular authenticated account.

The local matcher generates the versioned `phash-dct-64-v1` compact descriptor: a 64-bit perceptual hash represented as 16 hexadecimal characters. It compares descriptors with Hamming distance and accepts only distances of at most 8 of 64 bits. Distance is evidence, not a probability. Candidates are ranked deterministically, and no candidate is forced when none passes the threshold. Every candidate remains advisory and must go through Candidate Review and explicit user confirmation before any downstream action.

Current browser acquisition uses the file input (`accept="image/*"`, `capture="environment"`). On mobile web, `capture="environment"` is only a picker/capture hint; browser and operating-system behavior varies. The Android Capacitor app has native photo capture and single-photo gallery selection through `@capacitor/camera`; native camera support is acquisition only. No iOS project exists, and the Android project has not been built into or validated as an APK.

Every source feeds the same `ImageAcquisitionResult`: a browser-readable `Blob` and display name, or a distinct cancellation/error outcome. The browser file input adapts its `File`; the native camera adapter obtains the plugin's local web path and converts its response to a `Blob` without base64 or image persistence. The acquisition hook owns acquisition state and temporary preview-resource cleanup. `ScannerScreen` presents the image and manages user actions. Matching passes the `Blob` to the local matcher only after an explicit match action. Enrollment passes the still-selected `Blob` to the descriptor generator only after exact catalog selection and explicit confirmation, then saves only the compact descriptor and confirmed identity. The matcher decodes/prepares the image, generates the descriptor, and performs local reference matching. `CandidateReview` owns candidate selection and review. Only after explicit Candidate Review confirmation does `App` pass a runtime-confirmed local-reference candidate with a non-empty TCGdex catalog ID to the existing Binder action. Unsupported namespaces and candidates without IDs do not mutate the Binder; there is no automatic add or new catalog-resolution request.

Capacitor Core/CLI and Android are version 8.5.2; Camera is 8.2.4; App is 8.1.1. Android listens for the Camera plugin's `appRestoredResult` so a capture/gallery result is converted through the same Blob acquisition boundary if Android terminates the app while the external activity is open. The result is held in memory only until ScannerScreen consumes it. The prior selected image itself is not restored or persisted across process death. The generated Android project uses the plugin's external camera activity and system photo picker with `saveToGallery` disabled, so no camera or broad media/storage permission is declared. iOS has no generated platform project or usage-description configuration. This is an Android acquisition foundation, not an APK release or device-validated application.

For `phash-dct-64-v1`, `createImageBitmap` decodes the original image and canvas draws/resamples it to 32 by 32 before grayscale sampling. Browsers without `createImageBitmap` use the `Image` fallback and draw the decoded source into the same 32 by 32 canvas; this can decode the full source first. Both paths revoke temporary object URLs where applicable. The grayscale conversion and DCT/hash generation remain shared.

The automated test environment has no native image decoder or canvas implementation. Descriptor-to-matcher integration tests provide deterministic browser bitmap/canvas pixel fixtures while running the production pixel hashing, IndexedDB storage, and local matching path.

The provider-neutral sync boundary classifies Binder records, scanner references, and persisted application preferences as user-owned. Account-scoped references contain recognition descriptors and metadata only; raw scanner photos remain excluded. Preferences such as the currently persisted currency setting are still stored locally as before; classification does not activate sync. Device state and catalog caches remain local-only. Scanner raw photos, temporary scan files, unconfirmed candidates, recognition model caches, and third-party image archives are explicitly excluded from sync. Recognition processes the selected source image transiently on-device; it does not persist the source image.

V1 references remain in the app's local IndexedDB database and are not included in Binder collection data or transmitted. No server/shared reference store, photo upload, third-party image corpus, or automatic scan retention is provided. Google authentication and backend sync are future work; account ownership alone does not transmit data, and any future sync requires a separate authenticated sync implementation.
